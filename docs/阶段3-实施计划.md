# 阶段 3 实施计划：先安全读取，再形成手动更新闭环

状态：用户已确认实施，2026-09-20 手动采集工程版已实现；真实模型质量、三家真实岗位闭环及 T06 两端同步仍待验收。规划基线 `9666256`，当前证据见 [实现与测试记录](阶段3-实现与测试记录.md) 和 [评测报告](阶段3-评测报告.md)。以下保留原计划及完整门槛，不把部分验收当整体通过。

配套：[需求/契约/评测](阶段3-手动岗位采集需求.md)、[前两阶段复测](阶段1和2-复测记录-20260920.md)。此计划细化 T09–T12，不替换原后续来源扩充/每日调度路线。

## 1. 先做哪里

**第一步是 C0：选可读取的真实官方来源、标注样本、冻结契约。第二步 C1：只读检查并展示访问结果。** 这两步不需要真实模型 Key，也不向正式目录写岗位。先证明网页内容确实拿得到、异常可解释，再做模型提取。

顺序：

```text
C0 来源/金标/契约
 ├─ C1 安全读取API → C2 原文检查UI → 检查点A
 └─ C3 求职条件 → C4 提取与确定性规则 → 检查点B
             C1 + C4 → C5 运行/候选存储 → C6 差异预览UI → 检查点C
                          C7 原子接纳API → C8 接纳/岗位UI
                          C9 固定评测与真实试点 → 检查点D
T06 原生助手桥接 ──────────────────────→ 完整T12两端验收
```

不开新 Agent 并行修改同一存储或 HTTP 文件。执行中每个切片实际超过5个主要文件，就再拆小后继续。

## 2. 可执行切片

- 文件：`src/shared/collection-contract.ts`、`tests/fixtures/jobs_gold.json`、`tests/collection-contract.test.ts`、`docs/阶段3-来源验证.md`。

## 4. 关键风险与选择

| 风险 | 处理 | 不能承诺 |
|---|---|---|
| 官网仅JS/验证码/登录 | 标受限，换可读来源做试点，不绕过 | 任意招聘站都能采集 |
| 兼容模型JSON质量不同 | 程序验证+证据+固定集；可拒绝 | 连通即准确 |
| 同库迁移/接纳失败 | 升级前备份、短事务、唯一约束、故障测试 | 旧二进制直接读v2 |
| 预算与试聊竞争 | 复用同一模型锁/限流，运行预留上限，明确BUSY | 每分钟限流等于账单金额上限 |
| 原生助手仍读旧HTML | 单列T06，完整两端验收前不切默认入口 | TS新岗位立即出现在旧助手 |
| 小评测集过拟合 | 冻结/分层/来源分组，报告分母与真实构成 | 20例通过代表全网95%准确 |

实施前用户需要审阅：本规格的数据迁移与parser依赖方案、先网页后两端的交付顺序。真实服务/试点评测预算可在调用前再确认，**不要把Key发到聊天**。这些问题不妨碍当前离线规划，但会阻止把完整阶段3标为完成。
