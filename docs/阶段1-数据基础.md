# 阶段 1：数据基础规格与验收

2026-09-20。承接 TypeScript 迁移，限定在分享仓库；不改已安装台账。用户要求规划后实施并按计划验收，本轮不等待重复的开工确认。

## 目标与边界

同一套 TS 程序支持独立本机资料；进度与可更新目录分库；显式导入旧进度；目录进入数据库而非重新构建前端才可见。保留原界面、315 家初始公司字段/顺序和 7 个新增日期。

本阶段对应原 T01–T05 的数据范围。T06 原生悬浮窗迁移另验收，不将旧 Python 助手称为已同步。模型、搜索、采集、定时、岗位级进度、面试日历均不实现。不修改原 Codex 自动化，不导入真实个人库，不推送/合并。

## 数据设计

- `runtime.db`：资料 UUID；用 SQLite 独占事务持有运行锁，崩溃后操作系统释放锁，不靠删除可疑 PID 文件恢复。启动或导入均需取得锁。
- `qiuzhao.db`：保留 `applications(name,status,updated_at)`；增加 schema version 与导入回执，不把公司级状态猜成具体岗位状态。
- `catalog.db`：版本化公司表和别名表。公司具有稳定 ID、单调追加序号、原 10 字段、明确性质、渠道依据、首次收录日期（未知为 null）。规范化姓名/别名用于精确去重，不靠相似度或共享招聘平台域名合并公司。
- 可信 TS 目录只是初始化/后续追加种子。启动重复载入幂等，只追加缺少公司，已有字段/日期/序号不覆盖。任何修改既有公司字段的能力留待变更审核阶段。
- 前端只读目录服务；筛选、导出与详情都使用同一份已验证快照。目录失败显示错误，不回退到静态旧清单冒充加载成功。

每份资料目录在源码目录之外。规范化真实路径，拒绝旧 QiuzhaoLedger 目录（含软链接/目录联接指向）；数据库文件也不接受软链接。端口冲突直接失败，不复用未知服务、不终止其他进程。健康接口返回 profileId 和 instanceId，不返回本机路径。网页与接口校验资料身份，旧窗口不能在端口换成另一份资料后自动写错库。

## 接口契约

- 保留 `GET/POST /api/status` 的 statuses/updates 字段；附加 profileId。带 `X-Profile-Id` 的请求不匹配返回 409；写操作仍检查本机来源和令牌。
- `GET /api/catalog`：兼容公司行/新增日期，同时返回 schemaVersion、revision、公司元数据。它是有上限的完整筛选快照，不用于无限列表。
- `GET /api/companies?offset=0&limit=100`：分页数据及总数/修订号；limit 最大 500。
- `POST /api/companies`：本机会话令牌 + expectedRevision + company。仅追加，有效期/名称/分类/性质/URL 均在边界校验；别名命中返回原 ID、不覆盖；别名关联冲突或修订冲突返回 409。没有删除/批量覆盖 API。
- `GET /api/backup?kind=progress|catalog&profileId=<UUID>`：分别下载一致性快照。页面下载链接附带非秘密的资料 ID，避免旧页面在服务切换后下载另一份资料。未传 kind 时保留旧进度备份行为。
- 新错误采用 `{error:{code,message}}`；旧状态接口保留原错误形状。静态服务不暴露数据库、备份、源码和路径。

## 导入与恢复

离线命令明确指定 source 和 data-dir，服务运行时拒绝导入。源库以只读方式打开，经 SQLite 一致性备份形成快照；校验 schema、全部状态、名称、时间字符串和完整性。只将验证后的记录插入目标，不执行源库携带的触发器/DDL。

目标必须零进度且无导入回执。事务内逐条插入、全量比较 `(name,status,updated_at)` 后写回执并提交；任意失败回滚。备份保留以供核验，源文件永不删除或覆盖。不提供危险的“强制覆盖”参数；已开始使用的目标需另建资料，不倒灌回滚后续进度。

每步先出现失败测试，再实现、测试和提交。旧 12 项 TS 测试和 70 项 Python 回归保留；修改接口只更新必要的附加字段断言，不删除安全回归。没有配置 lint，因此不宣称 lint 已通过。

## 命令与代码约定

现有：`npm test`、`npm run build`、`python -X utf8 -m unittest -q`。
已实现：先 `npm run build`，再 `npm run profile:import -- --source <旧库绝对路径> --data-dir <独立目标资料目录>`；完整操作见 README。
使用 strict TypeScript、Node 内置测试与 SQLite，不增加依赖；外部输入 `unknown` 后验证，参数化 SQL，例如 `db.prepare('SELECT status FROM applications WHERE name=?').get(name)`。

Always：仅临时数据做破坏性测试、保持原事实/追加顺序、检查重开及完整性。
Ask first：真实资料导入/正式切换、替换原自动化、注册后台任务、远端推送。
Never：删除/重建真实旧库、强行覆盖非空目标、把网络失败视为岗位关闭、泄露私密资料。

## 风险和依据

Node 24 SQLite 仍提示 experimental，锁定当前运行范围并测试。不防御已经能以同一 Windows 用户任意篡改文件的恶意进程；不提供云端多用户认证。正式安装包及另一台机器验收不在本阶段的通过声明内。

依据：[Node SQLite](https://nodejs.org/api/sqlite.html)、[SQLite 一致性备份](https://sqlite.org/backup.html)、[SQLite 事务](https://sqlite.org/lang_transaction.html)。最终证据追加到本文件末尾，不用“保证绝无问题”代替测试范围。
