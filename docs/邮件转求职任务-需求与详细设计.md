## 1. 要解决什么问题

用户不应该记住“哪封邮件里还藏着一件事”。软件应把招聘通知整理成可执行、可追溯的任务：**要做什么、为哪家公司、何时开始或截止、在哪里操作、完成了没有、信息从哪里来。**

推荐流程：邮件同步后自动分析并保存候选；用户核对后生成正式任务；确定时间的任务同时显示在已有日历。时间不确定的事项可以确认为“时间待定任务”，不会凭空占用一个日历时段。

这里有三个不同概念，界面和代码都必须分清：

- **邮件候选**：模型或规则提出的事项，尚未被用户接受。
- **求职任务**：用户已经接受、需要跟踪的事情，例如参加一面、完成测评、预约时间。
- **日历展示**：任务时间的呈现，不是另外复制一条独立日程。

### 默认假设与边界

1. 延续本机优先；支持 QQ、个人 Outlook／Hotmail、学校／工作 Microsoft 365 的既有接入方向。
2. 首版自动提取、自动保存候选，**全部由用户确认成为正式任务**。清晰事项一键确认，缺字段的补填或保存为待定；不以模型自报置信度自动批准。
3. 不回复邮件、不代预约、不进入考试、不发送消息、不改已读状态，不自动把任务标成完成。
4. 保留既有公司、投递进度、手工日程、准备清单、主题与小窗行为。完成一项测评不等于“投递成功”，二者不联动修改。
5. 本阶段不做通用项目管理系统、不接微软云日历写入、不承担关机时的闹钟保证。

| `src/client/mail.ts`、`schedules*.ts` | 邮件核对面板、月历／列表，现有皮肤 | 一封多卡片、任务列表、窗口／截止的正确显示、来源与修改历史 |

特别说明：`Schedule.tasks` 目前只是 `{text, done}` 的**准备清单**，不能拿来塞正式笔试／面试任务，否则无法表达时间、来源、改期和独立状态。

当前协议去重主要用账户、message key 与正文摘要；Outlook 请求已使用 ImmutableId，但构造 key 时优先取 Internet Message-ID。需要保留服务商标识和内容版本，不把 Message-ID 当成可靠的全球唯一业务主键。

当前 HTML 清洗会压平段落；现有片段检查能证明“这句话在原文中”，不能证明模型把它解释成时间或公司就一定正确。本设计补结构和人工对照，不夸大证据校验能力。

## 3. 用户场景和功能需求

以下均为示例，不代表用户实际安排。

| 邮件内容 | 应形成的记录 | 禁止的误处理 |
|---|---|---|
| “9 月 25 日 14:00 北京时间，Agent 研发一面” | 一项面试任务；若年份未说明则先核对；确认后在对应时段显示 | 用收到邮件的时间充当面试时间 |
| “9 月 25 日前完成性格测评” | 测评任务，截止精度为日期；年份／时区待核对 | 擅自填 23:59 或把截止当开考时间 |
| “北京时间 9 月 23 日 09:00 至 25 日 18:00 可进入考试，限时 90 分钟” | 笔试任务，保留开放窗口及考试时长；可另外设置自己的计划时间 | 在整个 3 天窗口创建一场 3 天的考试 |
| “请于 9 月 22 日 12:00 前预约，面试时间另行确认” | 面试类的“预约”任务；不生成确定的面试开始时间 | 截止 12:00 被写成面试 12:00 |
| “先完成测评，再预约面试，另附设备检查要求” | 测评、预约分别记录；设备检查默认作为准备清单，原文有独立截止才建议独立任务 | 一封只留一个日期，漏掉其他行动 |
| “原周五面试改到下周一，同一时间” | 变更候选；必须核实相对日期、引用对象和原时区后展示差异 | 按当前公司名覆盖任意一场面试 |
| “取消原通知，以后续邮件为准” | 取消／待定变更候选；指定被取消对象，保留原始记录与历史 | 删除所有同公司安排 |
| “感谢投递”“岗位推荐”或验证码邮件 | 无关／不确定列表；不生成正式招聘任务 | 为提高召回，把每封邮件都建成待办 |

### 功能清单

- **F1 识别**：支持面试、笔试、测评；操作包括参加、完成、预约、提交材料。公司、岗位、轮次、时间语义、入口、要求分别提取。
- **F2 多事项**：单封可有 0～8 项候选；超过上限标记“可能未完整提取”，不悄悄截掉；可手工拆分或补建。
- **F3 核对**：原文和字段并排；区分“来自原文、规则换算、人工补充、未知”；可单条或勾选批量确认、忽略、恢复。
- **F4 跟踪**：任务新增、编辑、完成、重新打开、取消、删除与短期恢复；每次操作有版本和历史。
- **F5 展示**：同一任务出现在任务列表与对应日历位置；可按公司、类型、状态、日期、来源邮箱筛选。
- **F6 变更**：重发仅补充来源；改期／取消须核对目标；手工修改不被模型覆盖。
- **F7 失败可见**：同步失败、分析失败、信息不全、模型未配置、额度用完分别说明，保留手动记录入口。
- **F8 来源**：已确认任务可回看批准时的证据、原通知摘要及后续变更；清理邮件缓存不会删任务。

## 4. 架构：模型提建议，业务层决定能否保存

```text
QQ / Outlook / 粘贴通知
          ↓
来源落盘与去重 → 本地清洗、引用区识别、敏感内容处理
          ↓
规则候选 + 当前已授权模型（只输出结构化数据）
          ↓
类型 / 字段依据 / 时间 / 来源版本校验
          ↓
邮件工作区：多条候选 → 核对、补填、忽略或选择变更目标
          ↓ 显式确认
持久确认协调器
          ↓
schedules.db：任务 + 来源映射 + 修改历史 + 唯一回执（同事务）
          ↓
任务列表 / 日历投影 / 小窗摘要（同一条主记录）
```

不新增 Agent 工具链：分析模型没有浏览器、文件、数据库、发邮件或预约工具。已有 OpenAI 兼容接口继续使用，无需更换模型服务商。

### 4.1 模型与规则各做什么

- 模型负责语言理解：识别行动、区别预约和参加、分离多事项、提出改期关系和不确定点。
- 规则负责强约束：枚举、长度、日期合法性、时区换算、证据位置、链接安全、重复写入、版本检查。
- 用户负责确认：是否加入、日期疑点、变更目标、本人计划时间、完成情况。
- 提取结果无效时保留原文和错误，不把模型失败显示为“没有招聘事项”。

### 4.2 输出与证据

模型输出版本化 JSON：`schemaVersion`、`classification`、`actions[]`、`warnings[]`。每项含意图、事项类型、时间表达、证据引用；ID 和系统状态由后端生成，不能由模型指定已有任务 ID。

每个关键字段记录 `fieldPath + sourceVersion + partId + quote`；服务端根据纯文本原段落计算位置并核对。位置与原文不符则该字段不可标为有依据。来源规范化版本固定，避免清洗变化后高亮错位。

日期、时刻、时区、时间用途应联合核对：一句原文含“截止”不能仅因日期字面相同就支持“开始”。语义无法确定时保留疑点，不能靠字符串命中消除风险。人工更正注明人工来源，不伪造原文证据。

重新分析产生新分析版本，保留人工编辑草稿；已确认的任务不跟随模型重新生成。若已有未完成确认意图，先恢复或显式解决，不允许重分析抢写。

## 5. 任务模型与时间语义

以下是待实现契约示意，不是现有导出类型。生产接口必须使用运行时校验，不能只依赖 TS 类型。

```ts
type TaskKind = "interview" | "written" | "assessment";
type TaskAction = "attend" | "complete" | "book" | "submit_materials";
type TaskState = "pending" | "in_progress" | "completed" | "cancelled";

type TimePoint =
  | { precision: "date"; date: string; zone: string | null }
  | { precision: "minute"; date: string; time: string; zone: string | null };

type TaskTiming =
  | { mode: "fixed"; start: TimePoint; end: TimePoint | null }
  | { mode: "deadline"; due: TimePoint; boundary: "inclusive" | "exclusive" | "unspecified" }
  | { mode: "window"; opens: TimePoint | null; closes: TimePoint;
      durationMinutes: number | null; cutoffRule: "finish_by" | "start_by" | "unknown" }
  | { mode: "unknown"; originalText: string };

interface RecruitmentTask {
  id: string;
  revision: number;
  company: string;       // 可为空；界面明确显示公司待核实
  role: string;
  kind: TaskKind;
  action: TaskAction;
  title: string;         // 必填，例如“完成测评”，不是模型自动执行指令
  state: TaskState;
  timing: TaskTiming;
  plannedSlot: { start: TimePoint; end: TimePoint | null } | null;
  checklist: { text: string; done: boolean }[];
  uncertainties: string[];
  createdAt: string;
  updatedAt: string;
}
```

完整存储还包括来源映射、字段证据、地点、链接、原始时间文本、分析版本、人工更正、操作历史及删除标记。它们分表存储，不把私密原文塞进列表 API。

### 5.1 必须遵守的时间规则

1. **截止不是开始**。借鉴 iCalendar 对 DTSTART 与 DUE 的区分，但本期只写本地任务，不声称实现完整 iCalendar 导入／同步。[RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.2.3)
2. 只有日期不补 00:00／23:59；列表显示“日期级截止，具体时间未说明”。日期过去可标“截止日期已过”，不是精确到分钟的逾期判断。
3. 年份缺失先给待确认建议；不按当前年直接认定。相对日期优先参考可信发送时间与上下文，**不能无条件按接收／同步时间换算**；转发、延迟收信、日期矛盾需人工核实。
4. 时间有但时区不明，允许接受为“时区待核实”的任务，只进待定列表，不生成确定 UTC 时刻或定时提醒。界面默认北京时间不等于邮件声明北京时间。
5. 第一阶段继续支持北京、悉尼、UTC；其他明确 IANA 区域先保留原文并要求确认可支持的等价时间，不写死 `UTC+10` 为全年悉尼时间。
6. 真实时刻由后端从已确认的当地日期、时刻和时区计算，保留原始表达。DST 不存在／重复时刻必须显式解决，不挪动面试时间。切换“查看时区”仅改变显示。
7. 窗口与考试时长分开；只有“必须在关闭前完成”有明确依据，才计算参考最晚开始时间。不得把“允许最后进入”误判为“必须最后交卷”。
8. `plannedSlot` 是用户自己的执行计划，不改招聘方窗口。计划超出已知窗口提示冲突；必要信息未知则仅警告，不谎称已验证。
9. 截止日在不同时区可能不同；精确时刻按查看时区转换，日期级截止保持原业务日期并标来源时区，不做伪精确转换。

### 5.2 状态与统计

候选状态独立于任务状态：`queued → analyzing → review / failed → confirming → confirmed / ignored`，确认协调失败保留可恢复状态。

正式任务：待处理、进行中、已完成、已取消。“即将截止、已过时间、逾期、时间待核实”由时间和当前状态推导，不覆盖正式状态。固定面试开始时间已过，只提示“请记录参加情况”，不等于未参加或完成。

删除任务先软删除，默认保留 30 天可恢复；相同通知不会因删除而再次自动生成任务。准备清单全勾选不自动完成笔试；测评完成不自动完成面试预约。同一任务在日历出现多个标记，统计仍只算一项。

## 6. 数据基础、去重和异常恢复

### 6.1 存储选择：主记录一次保存，日历不复制

建议将 `schedules.db` 从 schema 1 兼容扩展到 schema 2，新增：

- `recruitment_tasks`：正式任务、记录修订号、软删除标记与时间字段。
- `task_sources`：任务与候选动作、来源版本、证据的映射。
- `task_history`：人工操作、改期、取消、批准批次及字段差异。
- `task_receipts`：确认／修改请求、内容摘要与结果 ID，唯一约束。

`mail.db` schema 2 新增候选动作、分析版本、同步／分析作业和确认批次。迁移表名可在实现时微调，但事务与唯一性约束不可降低。

**不在 `events` 再创建一份新任务副本**。新增联合读取服务，将旧手工事件和新任务转换成日历展示项，引用键分别为 `schedule:<id>`、`task:<id>:<marker>`。点击编辑回到各自主记录；列表、统计、小窗共享该读取层。

旧 `/api/schedules` 的结构和写入含义保持；旧客户端只能看到旧事件，升级后的工作台和小窗改读联合接口。不能把新版任务硬塞进旧 `kind` 枚举，再让旧代码错误解释。

既有已确认邮件和日历记录不重建、不重新分析。能通过原确认意图／回执证明关联的补充来源映射；不能证明的保留原样。旧事件被新邮件指向时可提示去原编辑器处理，首版不自动转换为任务、不自动覆盖；因此“历史日程自动改期”单列后续兼容增强，不冒充已支持。

### 6.2 去重不是只看公司和日期

- **消息身份**：账户隔离；QQ 保留文件夹、UIDVALIDITY、UID，Internet Message-ID 作为附加线索。UIDVALIDITY 改变需要受控重新扫描，不沿用旧 UID 游标。[IMAP 标识规则](https://www.rfc-editor.org/rfc/rfc9051.html#section-2.3.1.1)
- **Outlook**：使用账户＋ImmutableId；该 ID 在同一邮箱内移动文件夹时稳定，但跨归档邮箱／导出后重导入不保证相同，不能宣称永不变。[Microsoft 官方说明](https://learn.microsoft.com/en-us/graph/outlook-immutable-id)
- **内容版本**：规范化主题、发送者、发送时间及正文摘要；同邮件身份的内容变化作为来源新版本。摘要用于去重，不代表已加密。
- **候选身份**：后端生成稳定 action ID；重分析是新提取版本，不把数组序号直接当永久业务 ID。
- **跨邮件重发／转发**：公司、岗位、轮次、任务类型、业务编号、时间和证据综合给“疑似重复”；缺唯一依据时让用户合并，不能因为公司相同吞掉第二轮面试。
- **确认幂等**：候选动作＋批准版本唯一；不同浏览器生成不同请求 ID，也不能把同一动作重复建两次。保留处理墓碑，清理原文不清掉防重记录。

### 6.3 多任务确认与两库恢复

用户可先确认一项，其他仍待核对；邮件汇总显示“已处理 1/3”。同一批选中的操作全成或全不成，建议上限 8 项；批量中存在冲突则指出具体项，用户可取消勾选后重新确认。

1. `mail.db` 在事务中校验候选版本、锁定选中动作，持久化批准内容、目标版本、批次 ID 和稳定摘要。
2. `schedules.db` 一个事务提交任务、来源、历史与唯一回执；回执内容摘要不同则拒绝复用，不返回伪成功。
3. `mail.db` 回写已确认。步骤 2 成功但步骤 3 失败，重启按目标库回执补齐，不重复保存。
4. 已存在回执优先于旧版本冲突检查，使断线重试返回原结果；新内容不复用旧批准批次。
5. 目标修订变化则 409，保留用户输入并展示新旧差异；不要自动重试覆盖。无法恢复的意图留在“需要处理”，不能静默丢弃。

这种设计沿用现有跨库确认方式；不依赖两个 WAL 数据库的假想跨文件原子提交。删除、取消、修改与重新打开同样使用稳定命令和任务修订号。

### 6.4 迁移和数据保护

迁移前停写／暂停 worker、在线备份目标数据库并验证可读；各库事务迁移、`user_version` 检查。两库迁移非整体原子：任一失败时关闭新模块写入，保留成功步骤及备份，幂等重试完成后才启动 worker。

旧 `events` 的 ID、内容、准备清单和复盘逐条一致；`qiuzhao.db` 及公司目录、投递状态不得修改。未知更高版本直接拒绝，不能重建空库“修复”。回滚不直接覆盖整个 profile；保留已新增任务，优先停用功能／修复迁移。物理恢复需确认范围并保留恢复前副本。

## 7. 改期、取消与多封邮件关系

变更通知先进入候选。目标推荐只能是建议，不能让模型直接输出要更新的数据库主键。

- 展示原安排、新安排、支持原文及匹配原因；多个目标由用户选，不因同公司最近一条就自动匹配。
- 请求同时携带候选版本与目标任务修订号。另一窗口编辑、手工改时间或任务完成后，旧批准不得覆盖。
- 原邮件的“请忽略上一封”需要具体上下文。无可靠关联时保留为待核实通知，不批量取消。
- 多封变更时间顺序矛盾、邮件迟到、转发旧通知、已取消后又邀请，都展示时间线；收到较晚不等于业务版本更新。
- 取消保留任务、原因和历史，不物理删除；撤销取消由用户明确操作。邮件被删除或移出收件箱，仅影响来源可用性。
- 已完成任务遇到改期不自动重新打开；用户核对这是新一轮、补测还是错误通知后决定。

本地任务和日历都更新同一记录，所以不存在“任务变了，日历旧副本没变”的双写问题。

## 8. API 与模块边界

新增模块用严格 TypeScript，遵循现有 kebab-case 文件名与服务／存储／契约分层，不顺便重构整个 `http.ts`。外部 JSON 先作为 `unknown`，运行时验证之后进入服务；SQL 参数化；测试注入时钟、模型和网络。

建议模块：`shared/recruitment-task-contract.ts`、`server/recruitment-task-store.ts`、`server/recruitment-task-service.ts`、`server/recruitment-task-api.ts`；`server/mail-actions.ts` 管提取与字段依据；`client/recruitment-tasks*.ts` 管任务展示。具体文件按第 12 节拆分。

### 增量接口草案

| 新接口 | 语义 |
|---|---|
| `GET /api/recruitment-tasks` | 状态／类型／公司／日期筛选；游标分页，默认 50、最大 100；不返回邮件正文 |
| `GET /api/recruitment-tasks/:id` | 任务详情、修订号、有限来源摘要；证据按需单独读取 |
| `POST /api/recruitment-task-commands` | create/edit/complete/reopen/cancel/delete/restore；幂等命令，修改须 expectedRevision |
| `GET /api/recruitment-timeline?from=...&to=...&zone=...` | 联合旧日程、新任务；日期范围最大 93 天，返回展示项与主记录引用 |
| `GET /api/mail/:id/actions` | 多候选动作、版本、各项处理状态和疑点 |
| `POST /api/mail-confirmation-batches` | 批次、动作版本、批准后的字段、目标任务修订号；返回持久批次 ID |
| `GET /api/mail-confirmation-batches/:id` | pending/committed/conflict/failed、结果任务 ID；断线后查询 |

旧 `/api/mail` 的连接／同步／粘贴继续使用；旧单事件确认仅处理旧版候选。不能把新版动作交给旧“确认整封”路径重复执行。新协议显式带 `schemaVersion: 2`；缺失／未知版本返回错误，禁止降级猜测。

新接口统一 `{profileId, data}` 与 `{profileId, error:{code,message,fieldErrors?,retryable}}`。旧接口维持原格式，通过适配器衔接；不声称现有所有错误已经有 code。

错误类别至少：400 VALIDATION、403 FORBIDDEN、404 NOT_FOUND、409 REVISION_CONFLICT／ALREADY_DECIDED／SOURCE_CHANGED、429 BUDGET_EXHAUSTED、503 STORAGE_UNAVAILABLE。初次接受确认批次返回 202；只有目标库回执可证明写入时状态才是 committed。按钮转圈或模型 HTTP 200 不算保存成功。

所有接口沿用本地 Host/Origin、`x-app-token`、`x-profile-id` 校验。禁任意网络读取入口、任意文件路径、SQL 字段名和模型指定任务 ID。请求体有界、列表有分页、敏感证据不进运行日志。

## 9. 界面设计：现有日程模块内，一处管理

保持“薄荷石墨·轻量工作台”和现有角色皮肤，不重画整套 UI。**在面试日程模块增加“任务”视图，与月历／全部日程共享数据；邮件待确认仍是独立入口。**

### 9.1 任务视图

- 默认按“今天要处理／即将截止／时间待定／以后安排”分组，已完成与已取消默认折叠。
- 行内优先：事项名称、公司／岗位、时间语义、状态、主动作。不要用巨型统计卡挤占列表。
- 固定场次主动作“查看安排”；窗口任务“去完成／记录完成”；预约“打开预约入口”。只有用户点击才打开外链，打开不等于完成。
- 紧凑筛选：面试／笔试／测评、状态、来源；原筛选和滚动位置保留。
- 任务详情有原始通知、字段依据、准备清单、自己的计划时间、变更历史。敏感会议链接默认折叠，不放进首页通知文案。

### 9.2 邮件待确认

宽屏两栏：左侧原文，右侧事项卡片；顶部显示“识别 3 项，其中 1 项时间待核实”。点击日期字段高亮对应原文；模型建议、人工填写、未知用文字标签区分。

每项可独立补齐和确认。底部按钮写“确认加入 2 项”，不是模糊的“提交”。有疑点允许明确选择“按待定任务记录”，不能默认把缺失字段填掉。重新分析前提示保留人工修改；错误后输入不丢。

未配置模型显示“手动整理此邮件”，不阻塞记录；处理失败的邮件与无关邮件不能混成同一种空状态。

### 9.3 日历与小窗

- 固定任务画正常时间项；日期级任务画带“时间未定”的日期标记。
- 截止画“截止”徽标；窗口用轻量起止／有效期提示，不填满多天的全部时段。
- 时间或时区无法确定放待定区；手动计划和招聘方窗口明确区别。
- 小窗只显示接下来最多 3 项、待确认角标和“查看全部”；不扩展成第二个复杂编辑器。
- 角色只在空状态或轻提示出现，不抢焦点、不遮挡原文；需要用户处理的变更提醒去重，可在列表找回。

可用性验收：390px 窄屏无横向滚动，键盘可完成核对／确认／撤销，焦点回到触发项，表单有标签，状态不只靠颜色；兼容所有已有皮肤、明暗与减少动态效果偏好。

## 10. 邮箱同步、模型合作与非功能需求

### 10.1 本期与后续同步改进

R1 复用现有收件箱扫描与手动粘贴，**明确显示最近 30 天／最多 100 封的覆盖范围**。先补任务闭环，不把收件连接当成已完成全部增量同步。

R2 增强：预筛不只看标题；在用户授权读取范围内用本地受限正文预览补充线索，并提供“可能漏识别／手动选取”入口。不会把全邮箱逐封发给模型，也不允许发件域名白名单成为唯一筛选条件。

QQ 检查点绑定账户、文件夹和 UIDVALIDITY；落盘消息和推进检查点同事务。Outlook 按文件夹保存 Graph 返回的 nextLink／deltaLink，URL 当不透明状态使用，必须限制为官方 Graph 主机与预期路径；完整一轮结束才替换稳定 delta 检查点。[Graph 增量文档](https://learn.microsoft.com/en-us/graph/delta-query-messages)

途中断开从已落盘页恢复；游标失效执行有界补扫并显式显示未覆盖范围。单一收件箱先通过真实验收，多文件夹另行启用。不要因 API 返回了删除变更而取消面试。

### 10.2 模型和后台的运行约束

继续使用软件当前配置的模型，邮件专用传输授权绑定服务地址；换提供者后重新同意。每个分析作业记录 sourceVersion、promptVersion、modelConfigRevision，防止分析期间切换配置后错误归属结果。

分析作业需在任何异步等待前取得持久排他租约；租约带超时与代次，过期 worker 的迟到结果不能提交。手动分析和自动分析共用队列及预算；重启不把同一未决请求当成未调用。现有内存互斥不能直接当成新队列的持久锁。

保持现有保守预算：默认单轮最多 3 封、UTC 日最多 30 次尝试；界面明确重置规则，未来可调但不静默提高。同一次请求可抽取多事项，不为每个字段再请求模型。超时且上游是否执行不明时记为未知消耗，不无限自动重试；429 尊重等待时间，达到预算保留队列。

自动同步仍需明确开启，后端运行时每 10 分钟检查；未运行时不保证收到提醒。Windows 唤起沿用独立 engine 规划，不在此新增另一套开机任务或 Codex 自动化。

### 10.3 安全、保留期与可观察性

- 邮件是未可信输入，显示纯文本，不加载远程图片、不执行附件、不遵循邮件中的系统指令。
- API Key、授权码、验证码、登录链接 token 不传模型。邀请链接替换为本地占位引用，模型只返回 linkRef，确认后由本地安全 URL 映射还原；证据引用基于同一脱敏正文版本。首次发送提供脱敏内容预览；疑似认证邮件或秘密无法可靠分离时，阻止自动分析并转人工，不承诺规则能识别所有形式的秘密。
- 正文姓名／公司等不能保证完全匿名，授权页如实说明发送内容和实际模型服务地址；“本机存储”不等于“分析不出网”。不读取无关邮箱目录。
- 沿用原文和账户秘密的 Windows DPAPI；派生任务字段仍为本机 SQLite，**不声称全库加密**。邮件断开不自动删正式任务，也不等于服务商侧已撤销授权。
- 首版任务流程不解析图片/PDF/ICS 附件；标“附件未解析，请人工核对”。附件解析独立后续切片；不把只读到正文称为完整通知。
- 保留期按原方案补齐：未处理原文默认 30 天，确认／忽略后 7 天清理原文；清理前可见提示，候选元数据、必要证据和防重墓碑保留。用户可主动提前删除敏感缓存；清理不能删除待恢复确认意图。证据也可能敏感，提供单独清除，不承诺擦除已有外部备份。
- 日志仅含随机任务 ID、耗时、错误类别、分析版本、计数；无正文、主题、邮箱地址、会议口令。记录最后成功同步、覆盖范围、待分析、待确认、失败及下次尝试时间。

### 非功能验收目标

| 维度 | 目标与条件 |
|---|---|
| 数据一致性 | 重复确认、断线重试、三处崩溃恢复均无重复任务；无未经确认的正式写入 |
| 性能 | 在记录硬件的 Windows 本机上，2,000 条任务＋2,000 条邮件元数据；分页／月历本地 API p95 ≤300ms，筛选反馈 ≤500ms；不含网络／模型时间 |

## 14. 建议结论

可实现，而且现有邮箱连接、模型接口和本地日历都能复用。主要工作不是增加一个 prompt，而是补齐**多事项提取、任务时间模型、人工确认、幂等存储和同源展示**。

建议先批准并实施 R1：先任务基础，再邮件多事项核对，最后连到日历。这样不必等所有邮箱高级同步完成，就能先把真实通知整理成可用的任务；之后用冻结样本和真实小范围联调决定何时开放更强自动化。
