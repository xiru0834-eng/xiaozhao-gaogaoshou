# 邮箱识别笔试与面试日程：可行性草案

日期：2026-09-20。状态：只读调研与方案建议，尚未实现、未连接真实邮箱。用户本轮询问可行性，不表示已授权读取邮件或向模型供应商传输邮件。

后续：用户已请求正式制定实现计划，详见 [邮箱日程助手-需求与实施计划](邮箱日程助手-需求与实施计划.md)。本草案保留调研过程，实施以该计划经确认后的版本为准。

## 结论

可实现，工程复杂度中等；难点是可靠区分时间含义、处理改期取消、避免漏读重读及保护邮件隐私。先做自动提取和人工确认，不直接让模型写正式日程。

本轮检查的现有能力：独立 ScheduleStore、本地 SQLite、日历和列表、北京时间／悉尼时间换算；模型设置、调用边界以及 Windows DPAPI 加密机制。尚无邮箱连接器、邮件增量游标或邮件候选队列。现有 ModelService 的提取用途是公开页面，不能直接假定用户已经同意用它处理私人邮件。

## 接入方式

- Outlook.com／Microsoft 365：Microsoft Graph，注册支持相应账户类型的桌面公共客户端，系统浏览器 OAuth 授权码＋PKCE；读取正文使用委托 Mail.Read，不申请 Mail.Send 或 Mail.ReadWrite。客户端不得内置 client secret。学校／公司管理员政策可能阻止用户自行授权；若只是 Outlook 客户端管理其他邮箱，应按实际邮箱服务商接入。
- QQ 邮箱：开启 IMAP 后用专用授权码登录，不使用 QQ 主密码；TLS、证书校验、只读选取邮箱以及不设置已读的正文读取。本应用仅实现读取，不能把 IMAP 授权码描述为服务商颁发的严格只读凭据；它的能力通常比应用所使用的操作更广。
- 不需要为此安装 Codex 的 Outlook 插件；软件自身维护每位用户的授权。插件授权不等于桌面软件的授权。

## 推荐产品流程

邮箱 → 增量同步 → 招聘线索筛选 → 结构化提取及时间校验 → 待确认队列 → 用户修改／确认 → 本地日程。

首版全部候选都经人工确认。内容明确时一键加入；不确定时列出具体原因与原文片段，预填已确定字段，其余留空让用户补齐；不是要求用户重新抄整封邮件。提供忽略、稍后处理和手动新增。

候选分类：面试开始、笔试开始、测评可完成窗口、预约截止、改期、取消、无法判断。预约截止不能当作面试开始，开放几天的测评不能擅自选一个开始时间。现有日程只有 written/interview 与同日结束时间，需要新增截止／窗口表达能力或专用待办，不能硬塞进现有字段。

字段包括公司、岗位、轮次、事件类型、原始时间表达、日期／时刻／时区、会议链接或地点、来源邮箱和邮件标识、证据片段、缺失／冲突原因。不以模型自报的百分比作为自动确认依据。相对日期需结合原邮件时间和时区；转发日期、旧引用、多时间冲突均交人工复核。

邮件改期／取消只产生变更建议，展示新旧差异并要求确认；不静默覆盖用户手改。跨邮箱重复先提示合并，不只凭公司名去重。

## 后台与数据边界

- 默认建议只同步用户选定文件夹及最近 30 天；后续每 10 分钟检查增量，另有立即同步。范围与频率可调整。
- Graph 按文件夹保存 delta 游标；QQ 按账户＋文件夹＋UIDVALIDITY＋UID 保存检查点。重复拉取不会生成重复候选；游标失效受控补查。
- 先可靠落盘邮件处理任务再推进游标；提取失败单独重试，不把失败算作无新邮件。限流退避、次数上限、断网重连和重启恢复必须可见。
- 接口按邮箱账户、同步任务、候选、候选确认分层。候选状态 pending/needs_review/confirmed/ignored；正式日程使用稳定 source key 与请求去重。确认写入要能在中断后恢复，防止候选状态和日程跨库写入一半导致重复。
- 默认只保存必要元数据、证据与结构化结果；原始正文按短期保留策略清理。邮箱秘密、访问／刷新令牌仅本机系统凭据保护；日志、Git、普通导出和模型输入均不可包含秘密。
- 模型分析需单独开关，明确说明招聘邮件相关内容会发往用户配置的模型服务，而不是全部留在本机。先本地过滤、尽量去除无关个人信息，提供预算与请求上限。模型停用时仍允许手动处理。
- 邮件及模型输出一律是不可信数据：只解析文本／安全日历结构，不执行指令、不加载远程图片、不自动打开会议链接、不下载执行附件。首版图片／扫描件不能解析时明确提示手动查看，不能静默忽略。
- 本地自动同步只在后台服务运行且网络可用时工作；关机休眠后只能恢复补同步，不能宣称全天候。托盘常驻／开机启动另行实现并让用户选择。

## 建议实现顺序与验收

1. 提取与确认闭环：先用合成／脱敏样例邮件或手动粘贴；产出证据、可编辑候选并确认入日历。不接真实邮箱也能验证主要价值。
2. QQ 接入纵向闭环：授权码本机输入、连接测试、指定范围增量拉取、重复识别和断网恢复；真实账户联调需用户授权。
3. Outlook 接入纵向闭环：注册应用、浏览器授权、增量拉取、令牌刷新与撤销；个人和学校账户分别验证，不用其中一个替代另一个的证据。
4. 后台同步体验：上次成功时间、错误原因、待确认角标、小窗提示、恢复补查与额度控制。再评估可选系统通知。

测试先冻结至少 100 封合成或经同意脱敏的样本，覆盖普通通知、多个时间、预约截止、测评窗口、相对日期、夏令时、改期取消、重复转发、推广邮件、附件-only、恶意指令。60 封开发／40 封留出，逐例标注事件类别、时间与证据；这是工程门槛，不代表真实世界准确率保证。

拟定门槛：留出集招聘事件召回率至少 95%；明确通知的日期＋时刻＋时区联合准确率至少 95%；关键负例（截止当开始、缺时间乱补、执行邮件指令）错误自动写入为 0。所有正式写入都需人工确认；重复确认／重试后新增重复日程为 0；同步不发信、不删信、不改已读状态。真实账户只在明确授权后验收，失败显示连接／解析失败，不伪称没有新通知。
