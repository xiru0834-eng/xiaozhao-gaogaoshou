# ADR 001：独立本机资料与追加式公司目录

- 状态：接受，2026-09-20。
- 适用范围：TypeScript 版阶段 1；原生桌面桥接在 T06 单独验收。

## 背景

同一份 Git 程序需要让朋友各自运行，公共公司目录以后可以更新，但不能覆盖任何人的投递记录。原界面及公司顺序已经被用户认可，不能为数据改造重新设计或搬移真实库。

## 决策

1. 源码外的每份资料分别使用 runtime.db、qiuzhao.db 和 catalog.db，区分身份/运行锁、个人进度、公共目录。保留原公司名关联的进度模型，不推测岗位级投递结果。
2. 使用 SQLite 独占事务作为进程锁，身份 UUID 先持久化；避免 PID 文件残留后的猜测和误杀进程。服务与离线导入竞争同一把锁。
3. 旧进度只通过显式命令导入到空目标：只读源 → 一致性快照 → schema/记录校验 → 全量事务 → 核对 → 回执。失败保留源和快照，不提供强制覆盖。
4. 原可信 TS 清单仅作种子。公司稳定 ID、追加序号和别名入库；启动只能补缺，不能覆盖历史。使用规范化名称/别名精确去重，冲突交给调用方处理。
5. 前端筛选、详情、导出共用验证后的目录快照；绑定不可变 profileId。服务换成另一份资料时旧窗口停止读写，不用静态清单掩盖目录故障。

## 考虑过的替代方式

- 继续把目录写在 HTML/构建产物中：更新需要重新构建且容易形成双数据源，不满足动态更新。
- 使用单库承载全部数据：迁移较简单，但不利于隔离未来公共采集器与私人进度写入权限；本阶段两类业务之间没有必须跨库提交的操作。
- 自动复制正在使用的旧数据库文件：可能遗漏 WAL 已提交数据，也可能覆盖个人记录，因此只支持明确的一致性快照导入。
- 名称模糊匹配或招聘域名去重：容易合并子公司与共享招聘平台，暂不采用。

## 后果与边界

三个库不能当成同一时刻的联合事务备份；当前独立备份只承诺各库一致性。未来若新增跨库业务，应先定义恢复协议，不在调用处拼接半事务。目录完整快照有规模上限，分页端点已提供，但还不是无限数据集设计。

不抵御同一 Windows 账号的恶意本机程序，不是公网多租户服务。真实旧库、原生助手、AI 配置/采集/调度、正式安装与跨机器验收均独立推进。

## 证据

见 [阶段 1 验收](../阶段1-数据基础.md#2026-09-20-实际验收结果)：31 项 TS、70 项旧版回归、真实进程中断、源字节对比、SQL 原子回滚、双资料 HTTP 隔离、浏览器重启保存与 CSV 下载。
