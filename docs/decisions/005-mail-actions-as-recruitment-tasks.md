# ADR-005：邮件事项成为任务主记录，日历作为只读投影

状态：Accepted。日期：2026-09-21。用户已批准实施；核心任务链路已落地，发布与后续阶段状态见[实现与验收](../邮件转求职任务-实现与验收.md)。

## 背景

用户希望从邮件整理笔试、面试、测评任务。既有邮箱第一版只支持单封单安排的确定事件入历；预约截止和测评窗口还不能成为具有完整语义的正式记录。`Schedule.tasks` 是准备清单，不是任务实体。

本决策扩展 [ADR-003](003-mail-schedule-review.md)，保留“候选先核对、确认后写入”和跨库持久意图，不改变其隐私边界。

## 建议决策

1. 将候选动作与正式任务分开；一封邮件允许多个动作、分别确认。明确区分面试／笔试／测评和参加／完成／预约／提交材料。
2. 正式任务保存在既有 schedules.db 的新增表，带记录修订、来源、历史和唯一回执；mail.db 保存来源、提取版本和批准意图。
3. 新任务不再复制成 `events` 行。联合读取服务将旧日程和新任务投影到现有月历、任务列表及小窗，编辑回到原记录，计数按主记录去重。
4. 旧手工日程、准备清单和复盘不自动迁移。旧接口保持原契约，新前端显式使用联合读取；旧事件的复杂时间转换不默默发生。
5. 时间模型表达 fixed、deadline、window、unknown 和日期精度；自己的执行计划独立于招聘方的窗口。未知时间可成为待定任务，不制造精确提醒。
6. 所有正式写入须人工批准；变更必须核实目标和版本。跨库确认用 intent→目标事务回执→ack 恢复，不假设双 WAL 库原子提交。

## 备选与取舍

- **把截止和窗口塞入旧日程备注**：最快，但无法可靠筛选／提醒，还会误用开始时间，拒绝。
- **扩展旧准备清单为正式任务**：主从关系不对，独立测评会被迫挂在不存在的面试下，拒绝。
- **任务和日历各写一份记录**：界面接线简单，但改期、取消、删除会形成双写一致性问题，拒绝。
- **再建 tasks.db**：隔离清楚，却增加一个跨库写入参与者；与现有日程同属时间管理域，本期不采用。
- **全量迁移所有旧日程成任务**：可统一模型，但影响已有数据和兼容客户端；先做增量联合视图，不在这次强制迁移。
- **模型直接创建或更新**：少一次点击，错误安排代价高，且未有真实质量证据；本期不采用。

## 后果和发布约束

必须实现新的联合读取契约、时间语义、幂等批次、schema 备份迁移和旧客户端能力提示。新任务在未升级的旧客户端不可见，要在实际入口验收中明确；不能仅源码通过就宣称桌面小窗支持。

优势是同一事项只有一个可编辑主记录、旧数据保护边界明确，后续提醒和更多邮箱不需重复定义任务。代价是保留一段新旧记录并存期，历史事件的复杂变更需要人工处理。
