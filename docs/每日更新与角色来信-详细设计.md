# 每日更新与角色来信：详细设计与验收规范

日期：2026-09-21。产品：校招高高手。代码核对基线：`codex/typescript-migration` / `eba3e19`，含已有未提交改动。

**状态：设计文档，不是功能完成报告。** 用户已确认功能方向并委托设计；本轮先交付深入设计。未启用定时任务、未保存用户密钥、未改变投递数据。文中的新接口、表和组件均为拟实现项。

## 1. 要交付的体验

用户只需在自己的电脑配置 API、选择求职范围和每日时间，软件就能独立发现岗位及公开内推线索、核验来源、保留增量。运行结果生成一封“每日来信”，由当前选中的二次元角色轻量提醒。

核心承诺：

- 不依赖 Codex 会话或本任务；运行程序、个人配置和 API 足够完成已启用的流程。
- 用户能改变更新时间、时区、每日额度、提醒开关，也能随时停止。
- “一次性”指同一资料在一个提醒日最多自动展示一次，不是首次安装后只提醒一次。
- 真实成功、部分完成、失败和未运行分别展示。搜索命中不等于可投岗位；来源声称有效不等于推荐码验证成功。
- 公司历史顺序、个人投递状态、简历、邮箱账户和面试日历不被采集器改写。

使用场景：用户在 Windows 桌面浏览招聘网站，可能同时打开多个台账窗口。角色负责传递一段短信息，不抢焦点，不要求用户立刻处理，不持续晃动。

## 2. 现状与证据边界

| 能力 | 当前证据 | 本次需补齐 |

## 3. 功能范围与发布分层

### 3.1 完整目标

1. 搜索新线索，并复查存量岗位；记录来源、时间、适用批次和覆盖范围。
2. 生成差异候选；新公司只追加，岗位变化保留历史，个人状态保持不变。
3. 默认自动收集、人工确认。通过质量门槛且用户另行开启后，才允许“可信来源的新岗位自动收录”。
4. 每日时区调度、持久化预算、失败中断恢复和无窗口时的后台执行。
5. 角色来信、更新记录、时间设置、提醒预览和设置诊断。

“自动收集”会让新发现和日报每天更新；“自动收录”才改变正式岗位目录。两个开关分开标注，不能把需要用户确认的线索说成已经更新进正式台账。

### 3.2 按阶段交付，但不偷换整体完成标准

| 阶段 | 可实际使用的能力 | 仍不能宣称 |
|---|---|---|
| R1 | 手动搜索→核验/待核验→真实日报→手动查看来信 | 每日自动执行 |
| R2 | 后台服务运行时按时更新；一次性提醒；修改时间持久化 | 后台进程退出后仍会自己运行 |
| R3 | Windows 当前用户唤起、关闭页面后执行、启动后补查 | 关机、注销或凭据不可用时也能执行 |
| R4 | 真实来源与连续运行验收；可信新增自动收录可选 | 搜遍全网、所有内推码均可用 |

只有 R1–R3 通过且真实质量门槛满足，才能称本机“每日更新与提醒”已交付。R1/R2 的中间版本必须显示运行限制，不用一个已亮起的“AI 开关”掩盖缺失能力。

### 3.3 不在本次范围

云服务器、手机推送、QQ/微信消息、Windows 原生通知中心、在其他软件上方绘制新桌面角色窗、自动投递、验证码、登录绕过、付费内推、自动更新 Git 代码。旧原生悬浮窗联动是独立切片；本次角色来信首先在 TS 工作台里显示。

## 4. 页面与角色提醒设计

### 4.1 三个入口

- 侧栏“每日更新”：更新状态、下次执行、立即检查、最近日报和历史记录。
- 页内“自动更新设置”：更新时间、时区、范围、额度、自动收录政策、提醒开关。低频设置折叠，不扩大公司列表顶部。
- 右下角“每日来信”：运行终态形成日报后，在可展示的窗口出现一次。

不另建第二套换肤设置。复用 `appearance-model.ts` 的 `skinOf`、`characterArtwork`、`paletteFor`；已有角色素材本地加载。隐藏角色时仍显示文字来信，不把“隐藏角色”等同于“关掉提醒”。

### 4.2 来信构图

沿用“薄荷石墨·轻量工作台”的轻边框、清晰正文、克制色彩。桌面卡宽约 360–400px；角色头像 56–64px，不做大立绘遮挡操作。

```text
┌─────────────────────────────────────┐
│ [当前角色]  今日来信 · 09月21日      × │
│            今天的机会，整理好了。      │
│                                     │
│ 已收录 {n} 个岗位 · {m} 条待核验线索   │
│ 已检查 {c} 家 · 另有 {f} 个来源受限    │
│                                     │
│ [查看本次更新]          知道啦          │
└─────────────────────────────────────┘
```

以上为结构占位，不是实际更新数。计数来自持久化事件和接纳回执，不由模型编写。

角色语气只影响一句开场白，不能改变事实：薄荷“今天的机会，整理好了”；霁蓝“……整理好了，结果在这里”；绯樱“替你记好了，别漏看截止时间”；紫夜“慢慢看，今天的更新都在这里”；琥珀“新消息到啦，一起看看”。失败时统一转为明确的状态文案，不强行说好消息。

### 4.3 交互细节

- 不自动播放声音，不抢键盘焦点，不盖住正在打开的设置/确认对话框；延后到其关闭再申请展示。
- 只在页面可见、窗口获得焦点、用户近期没有正在输入表单时领取提醒。页面隐藏时不领取。
- 进入采用约 180ms 的轻微位移/透明度变化；无循环呼吸/跳动。减少动画偏好下直接显示。
- 来信不按几秒倒计时消失。点“知道啦”或 × 后收起；点“查看本次更新”进入对应日报并标已读。
- 不提供“十分钟后再弹”：它会与一次性语义冲突。需要稍后处理就去更新记录看未读。
- 狭窄窗口使用页内顶部紧凑来信，不固定覆盖底部按钮；长内容进入详情，不把整份日报塞进浮层。
- 自动提示使用 `aria-live="polite"`；完整按钮可键盘访问。自动出现不调用 `focus()`，关闭不把焦点跳到无关位置。
- 同屏旧 toast 与来信排队，不互相覆盖；提醒层级低于模态层，高于普通内容。角色图无障碍装饰隐藏，状态必须有文本。

### 4.4 状态文案与计数

| 状态 | 标题/内容原则 | 主操作 |
|---|---|---|
| 未配置/未开启 | “自动更新尚未开启”，不生成虚构日报 | 去设置 |
| 正在执行 | 页面显示当前阶段与已检查量；不提前消耗来信名额 | 查看进度/停止 |
| 完成且有增量 | 分列“已收录”“待核验”“内推线索”，不给三者求和叫可投岗位 | 查看本次更新 |
| 完成无增量 | “本次检查未发现可靠新增”，同时写覆盖范围 | 查看检查记录 |
| 部分完成 | “更新了一部分，还有来源待核验”，同时列成功与失败 | 查看受限来源 |
| 失败/被阻断 | “这次未完成更新”，说明网络、额度或配置原因 | 查看原因 |
| 用户取消 | “本次检查已停止”，保留已取得结果，不显示完成 | 查看已取得结果 |
| 延迟看到旧日报 | “上次更新 · 实际日期”，绝不标题写“今日” | 查看上次更新 |

日报还显示：计划/实际覆盖、未检查公司、发布时间无法确认数、重复数、排除理由、搜索请求和服务端搜索次数、模型用量、近截止提醒及各条原始链接。近截止提醒必须来自已核实截止日。

## 5. 每日时间的准确语义

### 5.1 默认和设置

默认推荐 `07:00 / Australia/Sydney`，允许用户调整。自动运行初始关闭；保存设置不发请求。启用按钮单独说明调用哪些服务、发送公开查询、最大每日调用量、数据如何处理。用户在本机启用后，不必每天再确认。

基础模式只有“每日更新时间”；提醒在这次更新终止且日报保存后出现，07:00 不是承诺 07:00 已完成。高级设置允许“在指定时间提醒”，但触发时间是 `max(日报就绪时刻, 当天提醒时刻)`。提醒时间早于更新时间时，界面直接解释会等更新结束。

推荐额外显示三项：下一次计划开始（带时区）、上一次实际开始、后台状态。服务器是时间判断的唯一来源；浏览器不能自行认为已过零点并触发收费调用。

### 5.2 调度算法

1. 后台启动和每约 60 秒唤醒 `checkDue()`；timer 只是唤醒机制，不是执行事实存储。
2. 用 IANA 时区计算当地日期与已保存的 `nextDueAt`；数据库事务领取 `(profileId, scheduleId, scheduledLocalDate)`，唯一约束挡住重入。
3. 成功领取后才预留预算并派发请求。一次父运行覆盖搜索、网页核验、提取和报告；不得分批重置预算。
4. 更新结束后事务保存终态、实际计数、日报和来信待投递记录，再计算下次时间。
5. 夏令时回拨的重复时刻取第一次；春季不存在的时刻顺延到该日第一个有效时刻。用固定时钟测试，不靠 `24*60*60*1000` 累加冒充当地每天。

时间算法封装在 `DailyClock`，输入 `now/timeZone/localTime/lastOccurrence`，输出下一次到期 UTC 与当地日键；实现时选择可靠时区日期算法并先覆盖 DST 测试。不得在 UI、Windows 任务 XML 和后端各实现一套时间逻辑。

### 5.3 边界行为

| 情况 | 确定行为 |
|---|---|
| 到点前改时间 | 若新时间仍在未来，今天按新时间；若已过去，下一个未来时段执行，不保存即扣费 |
| 今天已执行后改时间 | 今天不再自动跑；显示修改后的下次执行 |
| 改时区 | 当前运行及日报保留原时区；新时区从下一未来日程周期生效，不抹除日键和投递回执 |
| 首次启用时已经过点 | 默认下一个未来时段；用户可显式点击“立即检查”，不追补启用前历史 |
| 后台错过一次 | 恢复后只补最近 24 小时内一个已启用的到期周期；更旧周期标 missed，不连跑多天 |
| 运行时重启 | 已完成不再运行；中断运行标 interrupted；已发送且结果未知的收费请求不自动重发 |
| 手动检查与到期重合 | 同一执行队列，自动任务延后；通过统一日预算限制，不再开第二个无约束运行 |
| 修改筛选/Key/提供者 | 运行快照不混用配置；改变外发目标或凭据修订号使自动授权暂停，需重新启用 |
| 关闭自动更新 | 取消尚未发送的任务，已有结果保留；已发请求可能收费，不承诺撤销消费 |
| 睡眠/关机/注销 | 不保证执行；恢复按补跑规则处理。唤醒为单独可选权限，默认关闭 |

失败不整轮自动重试。用户显式重试有新 `requestId`、关联原运行、共享日预算；重复点击同一个请求 ID 不再次调用。

## 6. “每天一次提醒”不是一个前端布尔值

### 6.1 三种状态分别存储

- 运行状态：queued/running/completed/partial/failed/cancelled/interrupted/blocked。
- 日报状态：生成、最新修订号、已读时间；日报可一直回看。
- 自动展示状态：eligible → offered → dismissed/opened，另有 silent/superseded。展示过与读过不是一回事。

以资料为单位，保存 `(profileId, notificationDayKey)` 的唯一回执；`notificationDayKey` 固定为该通知周期的时区/当地日键，配置变更不能重建当天记录。每封日报也只能被自动提供一次。外观、换肤、清缓存和刷新均不清回执。

具体采用持久化提醒周期：每个周期保存不可变的 `windowStartAt/windowEndAt/zoneSnapshot` 和独立 ID，以当地午夜计算边界，不固定为24小时。改时区时，当前周期到原定结束时刻仍有效；之后才按新时区建立不重叠的下一周期。`notificationDayKey` 引用这个周期 ID，禁止简单拼接“新时区+今天”再发一个名额。软件长时间关闭时直接推进到包含当前时刻的周期，不为过期窗口补弹；固定测试覆盖向东/向西切时区和夏令时的23/25小时日。

### 6.2 多窗口流程及故障取舍

1. 可见且合适的页面从只读接口看到可提醒项；后台页面只更新未读角标。
2. 页面准备好组件后调用领取接口，后端以事务将该日名额置为 `offered`，返回固定 `reportId/revision/deliveryId`。
3. 多窗口并发只有一个能领取。失败方静默；BroadcastChannel 可减少多余轮询，但不承担正确性。
4. 领取成功后展示；关闭/打开详情分别幂等写回动作。关闭只代表不再弹，未读状态保留；打开详情才标已读。
5. 领取后浏览器崩溃，可能没看到浮层；为遵守不重复打扰，**不自动重新发放**，日报仍在未读列表。网络丢失可用同一 requestId 取领取回执，但重载的新页面不自动重放。

这里选择“最多一次自动展示 + 持久未读兜底”，不声称分布式的严格 exactly-once 可见展示。保存领取回执失败时不弹窗，避免每次刷新都重弹。

离线多天回来，只对最近 24 小时仍可提醒的最新日报尝试展示；更早记录只进历史未读。补跑和当天运行产生多封日报时合并成当天来信入口；当天已展示则只更新角标，不再次弹。手动预览明确写“预览”，不消费名额、不调用 API、不写日报。

## 7. 搜索、核验与自动更新的职责

```text
后端 timer / Windows dispatcher / 立即检查
                    ↓
         DailyCoordinator：日键、锁、预算、配置快照
                    ↓
         DeepSeekSearchProvider：只返回来源线索
                    ↓
         SourceReader / 站点适配：公司归属与原文证据
                    ↓
         提取 + 确定性规则：岗位、内推、时间、匹配
                    ↓
         候选去重 / 受控接纳 → 日报与通知 outbox
                    ↓
         工作台领取一次来信 → 查看详情/手动确认
```

### 7.1 官方搜索适配

- 原生搜索走 DeepSeek Anthropic 兼容 Messages，不往普通 Chat Completions 中硬塞开关。
- 首版固定官方主机；复用已经绑定该官方服务的密钥引用。任意自定义代理的 Key 不自动转发给官方。
- 仅接受真实 `web_search_tool_result` 内的结构化结果；普通回答里的 URL、模型自报“搜过”或没有搜索结果块，都不能算搜索成功。
- 保存请求尝试、服务端搜索次数与模型 usage；查询只包含公开公司、方向、届别、地区，不包含姓名、手机号、邮箱或简历全文。
- `page_age` 缺失就存 null；搜索查询里的“最近一天”不能冒充严格时间过滤。用真实原文日期决定新开，无法确认时写“首次发现”。

### 7.2 岗位与推荐码的独立核验

- 每轮分开做新线索发现和存量复核；公司按行业轮换，关注/近截止优先，显示实际覆盖率。
- 官方域名/ATS 租户必须核验；同是飞书/Moka 主域并不代表同一公司。未审阅归属进待确认，不能变成任意 URL 抓取器。
- 验证岗位 ID、AI/Agent/RAG 方向、2027 年 1 月毕业适用性、学历、经验、岗位开放及实际申请入口。
- 内推记录公司、码/公开链接原文、届别、招聘类型、适用范围、原帖、发布日期/过期日、核验时间。帖主身份未知就不写“员工已验证”。
- 不试投、不输入推荐码验证、不联系员工；“官方声明有效”和“来源称有效未实测”分开，未找到公开码保持空。
- 无法访问、403、超时和搜索不到不自动下架；明确官网停止申请才生成状态变化候选。

### 7.3 接纳与追加原则

默认 `review`：自动更新发现队列和日报；正式目录由用户确认。可选 `trusted_new_only` 需通过真实评测并在界面单独开启：只接纳已审阅官网、身份稳定、硬条件和开放证据完整的新增岗位。

旧岗关键变更、公司身份歧义、公司性质不明、内推码替换、未知毕业窗口均待确认。新公司只在末尾追加；同岗同城/多城身份根据岗位 ID 判断，不重排旧行。记录接纳主体、政策版本、来源证据和回执，不能写 `qiuzhao.db` 的个人状态。

日报“已收录数”只统计成功的接纳回执；“新线索数”按本次首次发现的稳定身份计数；重复 URL/转载只增来源证据，不重复加数量。人工后续收录可在详情追加事件，不能悄悄改写用户曾看到的来信快照。

## 8. 预算与外部调用安全

试点建议值（实现默认值，不代表本轮已授权收费）：每日最多 6 次搜索 HTTP 请求、每请求最多 1 次服务端搜索、20 次网页请求、6 次提取尝试、单轮 10 分钟。搜索和提取各请求限制输出 tokens；输入来源先裁剪和限长。页面显示小预算下仅覆盖部分公司。

- 全部手动/自动岗位操作共享持久化日预算；另有提供者全局限速，避免与邮件分析撞车。邮件数据与岗位正文不混入同一提示词。
- 费用账本使用固定 UTC 日桶，不因显示时区/更新时间变化而重置；当地日程另算。界面明确标出额度重置时刻。
- 请求前预留；发送后超时计 `unknown`，不退回可能已消耗的额度、不盲重试。HTTP 请求数和服务端搜索次数分列。
- 首版能严格保证的是派发请求上限；精确人民币和总 token 硬封顶还依赖供应商计费/输入计算，不能用字符估算冒充硬上限。建议同步设置提供者侧额度。
- 提醒文本使用本地模板和数据库计数，不为每封日报额外调用模型“写一句可爱的话”。
- Key 用既有 DPAPI 凭据机制，日志、任务参数、URL、导出和 Git 不带 Key。查询结果不能改变工具权限、提供者、预算或个人状态。
- 外部 URL 继续防 SSRF、重定向复查和正文大小限制；HTML/模型输出按不可信数据渲染。公开内推链接中的允许参数逐站识别，私人申请/登录 token 拒绝。

## 9. 后台运行与单一数据库拥有者

复用当前 `runtime-config.ts` 的资料独占锁。唯一 `LocalEngine` 拥有资料、HTTP、队列和调度；不另起第二个直接写同一数据库的定时 worker。

R2 的后端 timer 不依赖浏览器标签页。R3 的 Windows 任务每约 5 分钟唤起精简 dispatcher；它只请求引擎检查到期，不携带 Key、不自己搜岗、不把 Windows 本地时区当用户设置。

引擎存在时通过当前用户受保护 IPC 通知；不存在时隐藏启动。资料路径、profileId、引擎实例身份必须绑定。并发启动由资料锁拒绝失败方，不杀别人的进程，不降级到其他资料。IPC 仅暴露 ping/checkDue，不开放任意 URL/命令；若当前用户访问控制验收不过，R3 不发布。

注册/卸载只操作本应用、该资料的任务名。默认当前用户已登录，无管理员、无保存 Windows 密码、无 SYSTEM。开机后登录可触发检查；关闭页面不关闭引擎。“退出后台”明确提示暂停执行，且不让 dispatcher 立即违背退出意图重新启动。

状态必须可见：后台运行中／仅当前服务期间／系统唤起未安装／暂停／配置失效。关机、注销、休眠和系统策略限制不能被文案隐藏。

## 10. 数据模型与事务

新增运行状态、预算、日报与投递回执拟存 `catalog.db`，以免跨库承诺原子性。个人状态仍在独立 `qiuzhao.db`。迁移先一致性备份、版本检查、事务建表和完整性验证；禁止重建或清空个人库。

| 实体 | 关键字段与约束 |
|---|---|
| daily_settings | scheduleId、revision、enabled、localTime、timeZone、nextDueAt、notificationMode/time、notifyEnabled、acceptancePolicy、budgets、授权配置指纹、backgroundPausedAt |
| daily_occurrences | profileId、scheduleId、scheduledLocalDate、scheduledAt、zoneSnapshot；前三者 UNIQUE，状态、runId、lease/fence |
| discovery_runs / attempts | id、requestId UNIQUE、配置快照、阶段、来源任务、reserved/sent/settled/unknown、错误和用量 |
| discoveries / referrals | 稳定身份、原始链接、公司/届别/范围、证据、首次发现/最后核验、待核验原因 |
| usage_reservations / events | UTC 日桶、提供者、用途、attemptId UNIQUE、预留/结算、未知消耗 |
| daily_reports | id、occurrenceId、revision、runIds、实际覆盖、互不混淆的计数、报告生成时间、不可变展示快照、readAt |
| notification_windows | profileId、id、windowStartAt、windowEndAt、zoneSnapshot；同资料窗口不得重叠，由单一写入事务校验并推进 |
| notification_outbox | reportId、eligibleAt、expiresAt、dayKey、state；reportId 唯一 |
| notification_deliveries | profileId+dayKey UNIQUE、reportId、reportRevision、requestId UNIQUE、offeredAt、actionAt、action |

事务边界：领取周期与建运行一组；预算预留一组；候选/证据入库按来源一组；接纳继续使用现有回执事务；日报终态与 outbox 同事务；领取来信与当日名额同事务。任何网络请求都在事务之外执行。

全流程重启不能恢复旧的在途网络承诺：先将未知发送标 interrupted/unknown，再从已落盘证据继续本地核验/汇总；不重发收费调用。迟到结果必须校验运行 fencing token，失效实例不能入库。

日报与投递回执默认保留，不因关闭提醒清除；存储超过配额停止生成并提示归档，不静默删记录。将来增加清理时至少保留仍生效的去重墓碑。

## 11. 类型边界与本机 API

以下为待实现契约，不是现有端点。沿用项目严格 TypeScript、`unknown` 入参、运行时校验、结构化错误与 `AbortSignal` 风格；不因接口重命名破坏现有 `/api/collection-runs` 和 `/api/update-batches`。

```ts
type DailyRunState = "queued" | "running" | "completed" | "partial"
  | "failed" | "cancelled" | "interrupted" | "blocked";
interface UpdateCounts {
  discovered: number;
  verifiedJobs: number;
  acceptedJobs: number;
  referralLeads: number;
  duplicates: number;
  needsReview: number;
  failedSources: number;
}
type NotificationClaim =
  | { claimed: true; deliveryId: string; reportId: string; reportRevision: number }
  | { claimed: false; reason: "not_due" | "already_offered" | "disabled" | "expired" };
```

| 接口 | 请求/结果与幂等规则 |
|---|---|
| GET `/api/daily-settings` | 脱敏设置、revision、前置条件、nextDueAt、engineMode；不回传 Key |
| PUT `/api/daily-settings` | expectedRevision+严格 settings；保存不执行、不注册系统任务；冲突 409 |
| POST `/api/daily-activations` | requestId、settingsRevision、提供者/额度授权指纹；显式启用，未配置 422；注册 OS 任务另列状态 |
| DELETE `/api/daily-activations/current` | 幂等停用、撤销本应用任务和未发请求；已有数据保留 |
| POST `/api/discovery-runs` | requestId、expectedSettingsRevision、intent；返回202+runId，重复ID返回原回执 |
| GET `/api/discovery-runs/:id` | 阶段、真实计数、用量、错误；GET 不消费 API |
| POST `/api/discovery-runs/:id/cancel` | 幂等取消，显示已发送请求的费用边界 |
| GET `/api/daily-reports` | cursor+limit≤100；稳定排序；游标绑定筛选 |
| GET `/api/daily-reports/:id` | 带证据链接的冻结快照和后续本地接纳事件 |
| GET `/api/daily-notifications` | 只读候选及未读数，不占用名额、不标已读 |
| POST `/api/notification-deliveries` | reportId+requestId+expectedReportRevision；后端事务返回 NotificationClaim |
| PUT `/api/notification-deliveries/:id/action` | dismissed/opened；重复同动作幂等，不能回退状态 |
| POST `/api/daily-reports/:id/read-receipts` | requestId；主动看历史也可标已读，不制造自动弹窗 |

全部受既有 Host/Origin、会话 token、profileId 保护；列表上限、日期/时区/数值边界严格校验。失败统一 `{profileId,error:{code,message}}`。区分本地预算、提供者余额、鉴权、协议无搜索结果、站点受限和存储错误；不向前端返回凭据/堆栈。

通知领取成功但客户端没收到响应时，不创建新 ID 重领；通过同 ID 回执恢复。前端预览是本地明确标记的合成状态，不需要新后端写接口。

### 12.2 搜索与提取质量

至少 20 家公司、3 类公开来源试点；冻结至少 120 条人工核验记录（开发60/留出60，按公司与文档分组）。包含真实/合成比例、旧届别、实习、未知毕业窗、失效内推、转载、登录受限和注入样例。

目标：推荐精确率≥95%，人工可见试点目标的召回率≥80%；报告分母与置信区间，不称全网召回。跨公司/届别内推误绑定、没有原文却自动接纳、个人状态误改必须为0。有效样本或独立标注不足时不能开启自动收录；“全标未知”不能算质量通过。

连通性、离线规则、真实模型提取、真实来源和两次真实定时执行分别出报告；不能用改假时钟或模拟模型冒充真实连续运行验收。

### 12.3 UI 和性能

检查1440×900、1024×768、390×844、320×640；五种角色、明暗、角色隐藏、200%缩放、长中文公司名、0/大计数和错误信息。无水平溢出、无内容挡住主操作；正文对比≥4.5:1，焦点与按钮可见。截图必须实际打开检查。

本地设置/领取/列表 API 在隔离固定负载下 p95≤500ms，界面主线程不得执行抓取/数据库操作；日报1000条仍分页。自动运行到期检查误差目标≤90秒（引擎健康运行条件下），Windows 唤起目标另测，不把网络耗时算入本地性能。

## 14. 发布、安全与回滚

- 默认关闭自动执行和自动收录；无需模型也能继续使用原有台账、日历和邮件界面。
- 拟新增表通过迁移引入，备份恢复路径先在副本验证；不靠删除新表或重建个人库“回滚”。
- 部署前区分源码、dist、实际18765进程与旧18763入口；构建成功不等于已安装运行。
- 先隔离资料验收，再经明确启用操作切到本用户资料。旧Codex每日收集任务不静默删除；切换时明确哪一套负责哪份资料，避免双重消费/双写。
- 不自动把运行日志、密钥、私密URL、邮箱正文或个人DB推送Git；私有仓库也不是秘密存储。
- 停用只暂停任务和撤销本应用系统唤起，已收录内容、历史日报和个人状态保留；恢复旧版时先停新引擎并验证schema兼容。

产品方向已获用户同意。实施时仍需在本机界面完成的选择：实际Key绑定、收费额度、是否启用、是否安装Windows唤起、是否允许可信新增自动收录。不能把“同意设计并实现”当作无限期无限额外部调用授权。
