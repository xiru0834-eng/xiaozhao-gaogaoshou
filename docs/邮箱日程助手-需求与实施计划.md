# 邮箱日程助手：需求与实施计划

日期：2026-09-20。状态：**已获准实施；第一版分析—核对—入历闭环已实现，真实邮箱及真实模型质量验收未完成**。

本方案承接《邮箱识别面试日程-可行性草案》。以下保留完整目标，不以文档存在代替功能完成。当前实现范围、取舍与实际验收记录见《邮箱日程助手-第一版实现与验收》；未读取用户真实邮件、未替用户授权邮箱、未启用自动同步。

## 1. 目标与默认假设

在“校招高高手”的面试日程中增加“邮件待确认”入口：连接用户自己的 QQ／Outlook 邮箱，自动找出笔试、面试、预约截止及改期取消通知，展示原文证据和可编辑结果，用户确认后进入日历。

建议默认值（待审阅，不是已授权）：

- Windows 本机运行，每人使用自己的邮箱授权和模型配置，不设集中收件服务器。
- **第一版全部人工确认后入历**；确定的内容一键确认，不确定的字段标注原因并允许补填。
- 首次只查选定收件文件夹近 30 天；不扫描发送箱、垃圾邮件和全部历史。可后续选择更多文件夹。
- 手动同步先交付，自动同步默认关闭；显式开启后建议每 10 分钟检查一次。
- 默认查看北京时间并显示悉尼对应时间；邮件没写时区则标记待确认，不能把界面默认时区说成原邮件事实。
- 模型处理私人邮件使用独立开关，默认关闭；不继承公开岗位采集的模型授权。

成功不是“连上邮箱”，而是：新通知可追溯、疑点看得见、正式日程无重复、改期不静默覆盖、失败不会冒充没有新邮件。

## 2. 现有代码与可复用边界

本轮核对仓库 `%USERPROFILE%\Documents\GitHub\xiaozhao-gaogaoshou`：

|---|---|---|

| `src/client/schedules*.ts` | 月历、列表、编辑、准备清单与状态 | 待确认页、证据对照、改期差异和疑点提示 |
| `src/server/model-service.ts` | 模型配置与调用限制 | 私人邮件专用入口、单独同意、持久化额度及任务排队 |
| `src/server/model-secrets.ts` | Windows DPAPI 机制 | 独立邮箱凭据命名空间、账户隔离、撤销及删除策略 |

## 3. 功能需求

### 3.1 邮箱连接与同步

- QQ：本机输入邮箱及专用授权码、连接测试、选择文件夹、暂停、重新授权、断开。
- Outlook：浏览器微软官方授权，支持账户类型按实际注册配置展示；识别用户取消、管理员阻止、授权失效、令牌过期等情况。
- 连接测试只验证认证／文件夹访问，不自动触发全文读取或模型调用。
- 用户确认范围后手动同步；支持明确的新增、已处理、需人工查看、失败计数和最后成功时间。
- 不发邮件、不删除或移动邮件、不标记已读；不自动回复邀请、不代预约面试。
- 一封邮件可包含多场安排，生成多条候选并保留同一来源；不强制一封邮件等于一个事件。

### 3.2 识别与待确认

- 提取公司、岗位、笔试／面试、轮次、通知意图、日期／时间／时区、截止／有效窗口、地点、会议链接和准备要求。
- 每个关键字段带原文证据或“人工补充”标记；模型不能补造原文没有的信息。
- 分类包含新安排、预约邀请、测评窗口、改期、取消、无关邮件、无法判断。
- 明确区分：预约截止不等于面试开始；测评开放窗口不等于固定考试时刻；“届时通知”不能生成具体时间。
- 明确疑点：日期／年份／时区缺失、多个时间冲突、相对日期、转发中的旧引用、跨午夜、未知时区、只有图片附件。
- 按证据完整性和确定性校验展示“可核对／需补充／变更待确认”，不以模型自报置信度百分比自动放行。
- 候选可修改、确认、忽略、恢复待处理；忽略结果持久保存，重复同步不反复弹出。

### 3.3 正式日程与变更

- 保留原笔试／面试类别，新增时间语义：固定安排、预约截止、测评窗口、待定。
- 建议新增可选 `timing` 判别联合，不改变旧字段含义：`scheduled`、`deadline`、`window`、`unknown`；旧记录按旧规则读取，迁移前备份。
- deadline 只画截止标记，不产生虚假的开始时刻；window 支持跨日，日历与列表明确起止；未确定时间只进待定区。
- 改期／取消先关联目标日程，展示前后差异；目标不唯一时由用户选择，不按公司名直接覆盖。
- 用户手动修改过的记录遇到新邮件必须提示冲突。正式日程的完成状态不因邮件变化而被推翻。
- 邮件被删除、移出同步文件夹，不等于面试取消；只更新来源可用状态。
- 相同邮件重拉、确认按钮连点、网络断连重试、服务崩溃重开，最多写入一次。

### 3.4 UI 与提醒

保持薄荷石墨视觉，不改台账布局。日程模块增加“月历／全部日程／邮件待确认”切换，后者显示未处理数。

- 宽屏：左侧候选列表，中间纯文本证据，右侧可编辑结果；窄屏改上下排列。
- 日期、时区、疑点和“确认加入”突出；不只依赖颜色区分状态。
- 改期卡片显示旧时间 → 新时间，取消明确显示对象；信息不足时按钮进入补填而非静默保存。
- 新邮件角标／小窗待确认数不抢焦点。第一版不做全局弹窗、邮件提醒或系统关闭后的闹钟。
- 支持键盘、读屏标签、保存中防重复、错误保留输入、空状态、长公司名、深浅主题及 390px 窄屏。

## 4. 架构与数据流

```text
QQ IMAP / Microsoft Graph / 手动粘贴
              ↓
账户范围和增量游标 → 邮件处理任务（先可靠落盘）
              ↓
安全正文解析 → 招聘线索筛选 → 规则／日历结构解析
              ↓                       ↓
       可选模型提取 → schema＋证据＋时间规则校验
              ↓
         候选与疑点 → 人工修订／确认
              ↓
      幂等确认协调器 → schedules.db → 月历／小窗
```

确定性可提取的字段不强制调用模型；信息不足也不能为了节省调用静默丢弃。提供“未识别／处理失败”列表，用户可主动选取漏筛邮件。模型只返回数据，不带工具调用和写库能力。

### 4.1 模块与接口草案

新业务用 TypeScript；Python 仅小窗适配。推荐目录 `src/server/mail/`、`src/shared/mail-contract.ts`、`src/client/mail-*.ts`，与岗位采集分开。

```ts
type CandidateState = "pending" | "needs_review" | "confirming" | "confirmed" | "ignored";
type SyncState = "queued" | "running" | "partial" | "succeeded" | "failed" | "cancelled";
interface MailEvidence {
  messageId: string;
  part: "subject" | "body" | "calendar";
  excerpt: string;
}
```

协议适配器仅提供连接测试、列出文件夹、分页读取变化及读取正文，不提供 send/delete/move/mark-read。任何第三方响应均进行运行时校验。

| 本地接口（提议） | 职责 |
|---|---|
| `GET/POST /api/mail-accounts` | 脱敏列表／建立本地连接配置；不返回令牌或授权码 |
| `POST /api/mail-connection-tests` | 显式认证测试，返回可操作错误 |
| `POST /api/mail-oauth-sessions` | 建立短期授权会话，系统浏览器完成登录 |
| `POST /api/mail-sync-runs` | 显式同步或受控后台触发，返回 202 与任务 ID |
| `GET /api/mail-sync-runs/:id` | 读取进度、范围、部分失败与检查点 |
| `GET /api/mail-candidates?cursor=...&pageSize=50` | 有界分页、状态／账户筛选 |
| `GET/PATCH /api/mail-candidates/:id` | 证据详情／保存人工修订，检查版本 |
| `POST /api/mail-candidates/:id/confirmations` | 明确确认新建或变更，幂等请求键 |
| `POST /api/mail-candidates/:id/decisions` | 忽略／恢复，保留处理记录 |
| `POST /api/mail-disconnections` | 停止任务并清除本地授权；用户选择是否清理候选 |

所有业务接口沿用本地 host/origin、app token、profileId 检查；OAuth 回调单独使用一次性 state、PKCE、短期 loopback listener 验证，不能为回调放开整套 API。错误采用既有 `{profileId,error:{code,message}}` 结构；敏感上游错误不原样返回。

### 4.2 数据与崩溃恢复

- 独立 `mail.db`：accounts（非秘密配置）、folder_cursors、message_jobs、messages（必要元数据／受保护片段）、candidates、sync_runs、confirmation_jobs、budget_ledger。
- 凭据不进普通表／导出。邮箱授权码、OAuth 缓存和临时邮件内容使用独立 DPAPI 保护；每账户可清除。Windows 同一用户下的恶意程序不在 DPAPI 防护能力之外作保证。
- 待处理原文默认最多保留 30 天，确认／忽略后正文缓存最多 7 天；必要证据可留至用户清理。删除说明需涵盖备份副本，不承诺擦除已有外部备份。
- 正式日程保存在现有 schedules.db；其内容仍按现有本机存储方式保存，不声称整个 SQLite 数据库已加密。
- 用账户＋文件夹＋服务商标识去重。QQ 使用 UIDVALIDITY＋UID；Graph 优先稳定消息标识并按文件夹维护 delta 状态。Message-ID／正文摘要可提示跨邮箱重复，不能单独作为覆盖依据。
- 先落盘当前页处理任务，再在同一 mail.db 事务中推进同步游标。提取失败不丢任务，可有限重试；游标失效受控补查而非全邮箱无界重扫。
- 跨库确认不假装具有单事务原子性：mail.db 先持久化确认意图，schedules.db 将日程＋唯一来源回执在同一事务提交，最后回写候选完成。重启按回执恢复；测试每个中断点。稳定键基于候选 ID＋批准版本，改期为新批准版本，不冒充重复新建。
- 确认过程中编辑锁定；重复确认须匹配同一已批准内容。两窗口的候选与目标日程版本均验证，冲突不覆盖。

## 5. 接入、安全及运行约束

### Outlook

采用微软维护的 MSAL 类库和公共桌面客户端授权码＋PKCE；需注册应用、配置支持的账户类型和准确回调。申请读取正文所需 Mail.Read 及必要登录／续期范围，不申请发信、写信或日历写入权限，不在客户端内置 client secret。

个人 Outlook.com 与学校／公司 Microsoft 365 分别验收；组织可能禁止用户自行授权，遇到此情况明确标为管理员限制，不尝试规避。若 Outlook 只是客户端，账号实际是其他服务商，则按真实服务商接入。

### QQ

标准 IMAP over TLS，固定官方主机配置并校验证书，用户自行启用服务／生成授权码。READ-ONLY／EXAMINE 与 BODY.PEEK 路径验证不改已读标记；不实现 SMTP。应用只读不等于授权码自身是严格只读，设置页须说明并提供撤销方法。

### 邮件与模型的信任边界

1. 邮件及附件内容是数据，不是操作指令；禁止按邮件要求访问本地文件、调用系统或上传其他邮件。
2. 展示纯文本与经过验证的链接，不渲染活动 HTML、不加载跟踪图片、不自动访问会议或招聘链接。
3. 首版支持正文及有限 `.ics` 日历结构；大小／MIME／解析深度均受限。图片、PDF 扫描件、密码附件不能解析时进“需人工查看”，不执行附件或跟踪外链。
4. 邮件发送给模型前单独同意；展示实际服务地址、发送内容范围与可关闭开关。凭据、验证码等认证秘密不进入提示词，会议访问口令尽量本地处理。相关正文的个人信息不能承诺绝对脱敏，需如实说明。
5. 新依赖限定 IMAP、MIME／ICS、OAuth 所需成熟库；实施时审查维护状态、许可证、传递依赖及漏洞，固定 lockfile，不手写完整协议解析器。

### 建议非功能门槛（实施前可调）

| 维度 | 目标／限制 |
|---|---|
| 可靠性 | 重复同步／重复确认新增重复日程为 0；重启恢复全部已落盘任务；现有投递记录不变 |
| 本地体验 | 1,000 条候选下分页本地读取 p95 ≤300ms、搜索交互 ≤1s；不把外网时间算入该目标 |
| 网络 | 每账户单次同步互斥；超时、有界重试；尊重服务商 Retry-After，超出本轮预算则延期 |
| 初始范围 | 近 30 天选定文件夹，每页最多 100 封；首轮安全上限建议 500 封，超出显示尚未扫描并让用户继续 |
| 解析限制 | MIME 单封建议上限 5MB；超限／截断必须标记需人工，不把片段称为完整邮件 |
| 模型消耗 | 建议默认最多 50 次／日、单轮 20 次、单请求 30 秒；持久化计数和 token 记录，实际费用取决于用户服务；无授权不开启 |
| 可观察性 | 展示最后成功／最近失败／待处理／部分完成；日志只有脱敏标识与错误类别 |
| 后台 | 默认关闭；开启后建议 10 分钟轮询，关机不运行，唤醒补一次增量，不密集补跑历史轮次 |
| 数据保护 | 所有测试先用临时 profile；生产迁移在线备份＋完整性检查；禁止覆盖或重建 qiuzhao.db |

预算规则由设置明确展示，用户可调；达到上限保留队列，不静默丢弃候选。前台手动分析和后台共用额度；首次真实模型联调需另行同意并固定小额度。

## 7. 评测集、标准与验收证据

### 7.1 固定数据集

先建至少 100 封合成／经同意脱敏样例：60 开发、40 留出，按邮件模板／线程分组切分，防止只换公司名的数据泄漏。每封可含 0 至多条金标事件。至少覆盖通知、推广、缺日期、缺时区、多时间、预约截止、测评窗口、跨日／夏令时、改期取消、重复转发、附件-only、提示注入。

标注字段：应否产生候选、事件意图、所有时间语义、时区、应保留的未知、证据位置、目标关联、是否必须人工查看。留出集不参与提示词调优；失败后发布新版本评测并补充独立保留样例，不回头删难例。

### 7.2 拟定发布门槛（目标，尚无结果）

| 指标 | 门槛与计算 |
|---|---|
| 招聘事件候选召回 | 金标相关事件中被发现且可查看的比例 ≥95%；报告 TP/FN 与样本数，处理失败不算成功发现 |
| 候选精确率 | 判为可核对招聘安排的候选中真实相关比例 ≥95%；不能把全部邮件转待确认来掩盖低质量 |

## 8. 安全发布与回滚

先临时 profile → 单账户人工试点 → 双邮箱 → 显式后台启用。旧 applications 不变，不整理历史公司行。

迁移前在线备份并核验；新 schema 版本不被旧代码误读。回滚先停用邮箱 worker，保留用户新产生的日程，不能直接覆盖整个 profile 回到旧备份。跨库日志与回执用于恢复；若必须恢复数据，由用户确认恢复范围。

每人独立授权，不共享维护者的令牌／授权码。对外分发前明确 Outlook 应用注册归属、支持账户类型、隐私说明及可能的管理员批准；设置里的“断开”只能保证本机停止使用并删除缓存，服务商侧撤销入口单独提供。

## 9. 开工与用户参与点

**建议先做 M00 → M01/M03/M04，再逐步做到 M08。** 先交付可实际使用的“粘贴通知—检查疑点—确认入历”，同时提前核实 Outlook 注册条件；不一开始扫全邮箱或做常驻任务。

计划获批准不等于邮箱与云模型数据传输已授权。到对应阶段需要用户：

1. 确认 Outlook 是个人邮箱还是学校／单位邮箱；只影响适配和真实测试，不阻碍阶段 A。
2. 在软件本机输入 QQ 授权码、在微软页面完成登录；不要发到聊天。
3. 选择读取范围，以及是否允许相关内容发给当前模型服务。
4. 真实联调通过后，选择是否启用后台同步和开机启动。
